Release System

ChangeSet Architecture

This document describes the implemented workflow for writing PR change sets, staging them in .changeset/, turning them into CHANGELOG.md entries, archiving consumed files, and publishing versioned GitHub Releases from tags.

1 Repo-level product version until add-ons become separately shipped packages.
3 Separate ledgers: planned work, unreleased change intent, released history.
Skills Agents run the change-set and release workflows; scripts do the repo mutations.

System Overview

This repo uses a custom archived changeset workflow. Pending files in .changeset/*.md are the source of truth for unreleased user-facing change notes. CHANGELOG.md is the durable public ledger. vX.Y.Z tags and GitHub Releases are the public release snapshots.

The package remains private: true and is not published to npm. The release artifact is the source snapshot, the public site deployment, and the human-readable release record.

SemVer is the versioning policy. The current package.json value, 1.0.0, is the baseline changelog entry. During release preparation, pnpm changeset:version bumps from that value and archives consumed changesets under .changeset/released/<version>/.

There is no separate agent command named release. The mutating release step is pnpm changeset:version -- --yes. The surrounding commit, tag, push, deployment verification, and GitHub Release work are normal maintainer steps.

Track work

GitHub issues, PRDs, and project labels describe planned or active work.

Track change intent

.changeset/*.md files travel with PRs and explain the release note.

Track releases

CHANGELOG.md, tags, and GitHub Releases describe shipped snapshots.

Agent Skills

The intended day-to-day interface is an agent skill. The package scripts are the repo-local machinery that the skill validates or runs after it has inspected the PR or release state.

Write a PR change set

$write-change-set

Run this when the PR is ready for review or ready to merge and carries its change set with the code. The agent inspects the branch, writes or updates one .changeset/*.md file, and runs pnpm changeset:check-pr.

Plain-language prompt: Write the change set for this PR.

Prepare a release

$prepare-release

Run this after one or more PRs have merged and pending files exist in .changeset/. The agent previews the next version, runs validation, consumes pending change sets into CHANGELOG.md, and archives consumed files under .changeset/released/<version>/.

Plain-language prompt: Prepare the next release from pending change sets.

Codex invocation

In Codex, skills are invoked with $skill-name, not slash commands. Use $write-change-set and $prepare-release. Claude can use the same skill names through its installed skill surface or a plain-language prompt.

Underlying Commands

These are the real commands in package.json. Agents use these commands inside the skills, and maintainers can run them manually when they want direct control.

In a feature or fix PR

pnpm changeset:add
pnpm changeset:check-pr

Run these when the PR changes visible behavior, app-author contracts, storage, deployment behavior, or public docs. Update the same changeset if the PR changes during review.

For a general validation pass

pnpm changeset:status
pnpm changeset:check

status previews pending release notes and the next version. check validates every pending changeset file without requiring the current branch to contain one.

To prepare a release

pnpm changeset:version -- --dry-run
pnpm test:unit
pnpm build
pnpm changeset:version -- --yes

The dry run shows the next version and changelog output. The --yes run mutates package.json, CHANGELOG.md, and .changeset/released/<version>/.

After release files are reviewed

git add package.json CHANGELOG.md .changeset/
git commit -m "chore: release vX.Y.Z"
git tag -a vX.Y.Z -m "vX.Y.Z"
git push origin main --follow-tags

Replace X.Y.Z with the version produced by pnpm changeset:version. Verify production before publishing the GitHub Release from that tag.

System Map

The workflow uses three records with different jobs. Issues and PRDs plan work, changesets describe unreleased user-facing changes, and the changelog plus tags describe what shipped.

Planned Work

GitHub issues, PRDs, and discussion docs describe ideas before they land. They can be split, renamed, merged, or abandoned without rewriting release history.

Lives in: issues, PR descriptions, planning docs.

Unreleased Intent

Pending changeset files describe what a merged PR will mean to users, app authors, or operators. They are short, explicit, and version-aware.

Lives in: .changeset/*.md.

Released History

The changelog and GitHub Releases describe what actually shipped. Archived changesets preserve the source notes that produced each release.

Lives in: CHANGELOG.md, .changeset/released/<version>/, and vX.Y.Z tags.

Files and Ownership

Each artifact has one owner. Avoid making PR labels, commit titles, release notes, and changelog entries compete as sources of truth.

Artifact Purpose Owner / creation time
.changeset/*.md Unreleased release intent: package, bump type, and human-facing summary. Written in the feature/fix PR before merge.
CHANGELOG.md Permanent release ledger with version sections and dates. Generated by pnpm changeset:version -- --yes, then edited and committed by the maintainer.
package.json version Repo-level product version for tooling and optional in-app display. Updated only by pnpm changeset:version -- --yes.
vX.Y.Z Git tag Immutable code pointer for a public release snapshot. Created after the release commit lands and production deploy is verified.
GitHub Release Public release page with curated notes, source archives, compare link, and assets. Created from the tag; uses the changelog section as the starting point.
GitHub issue / PR labels Planning, triage, release-note categories, and optional omission reasons. Maintained during issue and PR review. Labels are not the changelog source.

PR Workflow

Each release-worthy PR carries the release note that will eventually become part of CHANGELOG.md. The changeset describes the final user-visible result, not every implementation step.

Change Build the feature or fix with the normal tests and docs.
Add note Run pnpm changeset:add or create one file in .changeset/.
Review Check the bump type, category, and human-facing wording.
Validate Run pnpm changeset:check-pr for release-worthy PRs.
Merge Merged changesets accumulate on main until release time.

Feature PR rules

Add a changeset when the PR affects users

  • New apps, windows, menus, document handlers, desktop behavior, or store flow.
  • Bug fixes users can observe.
  • Storage, backup/restore, document routing, or app registration behavior.
  • Public app-author docs or manifest contract changes.
  • Security fixes, dependency updates with runtime impact, or deploy behavior changes.

Skip a changeset when the PR is invisible

  • Test-only changes.
  • Internal refactors with no behavior or public contract change.
  • Development tooling changes that do not alter install, build, deploy, or runtime.
  • Typo fixes in internal docs.
  • Dependency lockfile churn with no shipped effect.

Example changeset

---
type: minor
category: Added
issue: #123
---

Add folder-addressable Finder windows so Desktop folder aliases open the folder
the user clicked instead of focusing an unrelated Finder window.

Release Workflow

A release maintainer consumes the pending changesets when they want a new public snapshot. This is a local command sequence today, followed by normal Git and GitHub release steps.

Preview Run pnpm changeset:version -- --dry-run.
Verify Run pnpm test:unit, pnpm build, and any relevant browser checks.
Consume Run pnpm changeset:version -- --yes from a clean working tree.
Review Edit CHANGELOG.md wording if needed, keeping archived source notes.
Publish Commit release files, tag vX.Y.Z, verify production, then create the GitHub Release.

Release maintainer command sequence

pnpm changeset:check
pnpm changeset:version -- --dry-run
pnpm test:unit
pnpm build
pnpm changeset:version -- --yes
git add package.json CHANGELOG.md .changeset/
git commit -m "chore: release vX.Y.Z"
git tag -a vX.Y.Z -m "vX.Y.Z"
git push origin main --follow-tags

The only command above that updates release files is pnpm changeset:version -- --yes. It updates package.json, prepends a version section to CHANGELOG.md, and moves consumed changesets into .changeset/released/<version>/.

Versioning Policy

SemVer is useful only after you define what compatibility means. For Terminal, the public surface is broader than package APIs.

Major

  • After 1.0.0, breaking public app/add-on manifest contracts.
  • Data or backup format changes that require user action or cannot be rolled back.
  • Dropping documented browser/runtime support.
  • Removing a released user workflow or app surface.

Before 1.0.0, use major only for deliberate public compatibility resets.

Minor

  • New apps, document handlers, OS features, settings, or user workflows.
  • Backward-compatible additions to the app manifest or AppContext contract.
  • Major visible improvements that are not bug fixes.
  • Deprecations that warn before removal.

During 0.x, most meaningful public contract shifts are minor.

Patch

  • Bug fixes, visual corrections, small copy fixes, and browser compatibility fixes.
  • Security fixes that do not change public contracts.
  • Runtime dependency updates that preserve behavior.
  • Documentation clarifications for existing behavior.

Patch releases can happen immediately when production is broken.

Starting version

Keep 1.0.0 as the baseline version because it is already the repo's declared package version. The first consumed changeset release will bump from that baseline and preserve the initial release entry in CHANGELOG.md.

Changelog Shape

Use Keep a Changelog categories, but allow Terminal-specific notes where users need migration or browser-storage context.

Canonical sections

  • Added for new features.
  • Changed for behavior changes.
  • Deprecated for planned removals.
  • Removed for removals.
  • Fixed for bug fixes.
  • Security for vulnerability fixes.

Terminal-specific additions

  • Migration Notes when localStorage, IndexedDB, backup, or restore behavior changes.
  • App Author Notes when manifest, AppContext, or document-routing contracts change.
  • Known Issues when a release intentionally ships with a visible limitation.
  • Upgrade Notes when self-hosters need an action beyond pulling the tag.

Tags, GitHub Releases, and Deploy Timing

GitHub Releases are based on Git tags. Treat tags as immutable public anchors and release pages as the announcement layer.

Tag policy

  • Use vX.Y.Z tags for public releases.
  • Do not move or rewrite release tags.
  • Prefer annotated tags for manual releases.
  • Use vX.Y.Z-alpha.N only when you need public prerelease testing.
  • Do not use package-name tags like terminal-bli-net@0.2.0 for the public release surface.

Release page policy

  • Start from the matching changelog section, then edit for readability.
  • Include the compare link and any notable screenshots or migration notes.
  • Mark prereleases in GitHub when using alpha, beta, or release-candidate tags.
  • Use GitHub security advisories for vulnerabilities that need coordinated disclosure.
  • Let GitHub attach source zip and tarball archives automatically.

Deployment alignment

If Cloudflare Pages deploys automatically from main, the release tag points at the release commit only after the production deployment is verified. If production deploys move into GitHub Actions, release creation waits for the build, tests, and deploy job.

For now, the pragmatic path is a two-stage flow: run the local changeset version command, commit the generated release files, then create the tag and GitHub Release after the production deployment is verified.

Feature Tracking

Changesets are not a roadmap. They are the final release-intent note attached to work that is about to merge or has already merged and is waiting for release.

Issue and PR labels

  • type:feature, type:bug, type:docs, type:chore.
  • area:terminalos, area:apps, area:storage, area:workers, area:docs.
  • release:major, release:minor, release:patch, release:none.
  • needs:changeset when a PR appears release-worthy but lacks one.
  • changelog:skip only for explicit maintainer-reviewed omissions.

PR template additions

  • Release impact: major, minor, patch, none.
  • Changeset included: yes, no, not needed.
  • User-facing summary in one sentence.
  • Storage model changed: yes or no.
  • Docs and in-app copy updated when storage, backup, routing, or app registration behavior changes.

Maintenance

The system is repo-native and already wired into package scripts, docs, tests, and the PR template. Maintenance is mostly about keeping change-set decisions explicit.

Implemented files

  • scripts/changesets.js is the CLI entry point.
  • scripts/lib/changesets.js parses, validates, versions, and writes.
  • scripts/lib/changesets.test.js covers the release logic.
  • .changeset/README.md documents the file format for contributors.
  • docs/changesets.md is the compact operating guide.
  • .github/PULL_REQUEST_TEMPLATE.md prompts for change-set status.

Maintainer responsibilities

  • Keep one changeset per release-worthy PR unless there is a clear omission reason.
  • Review the generated changelog before committing release files.
  • Do not delete consumed changesets; keep the archived folder committed.
  • Do not move published release tags. Ship a follow-up patch if needed.
  • Update architecture docs and in-app copy when storage behavior changes.

Automation and agent notes

Required now

  • No GitHub Action is installed for the first version of this system.
  • PR authors and agents follow AGENTS.md, docs/changesets.md, and .changeset/README.md.
  • Release-worthy PRs run pnpm changeset:check-pr; release maintainers run pnpm changeset:version -- --dry-run before consuming changesets.

Not installed

  • There is no automatic PR check that runs pnpm changeset:check-pr; authors, agents, and reviewers run it directly.
  • There is no GitHub Actions release workflow that extracts CHANGELOG.md and creates the GitHub Release.
  • Tagging and GitHub Release creation remain manual maintainer steps after deployment verification.

Checklists

These are the habits that keep the system useful after the initial setup.

PR author

  • Decide whether the PR is release-worthy.
  • Add a changeset for user-facing, app-author-facing, storage, or deploy-impacting work.
  • Use user language, not implementation-only wording.
  • Choose the smallest defensible bump type.
  • If storage changes, update architecture docs and in-app copy.

PR reviewer

  • Check that missing changesets are intentional.
  • Check the SemVer bump type.
  • Check whether migration or app-author notes are needed.
  • Check that release notes are clear to someone who did not read the diff.
  • Apply release:none or needs:changeset labels when useful.

Release maintainer

  • Review the generated release files, especially CHANGELOG.md.
  • Group or rewrite entries when raw changesets are too granular.
  • Run the normal build, unit tests, and relevant browser checks.
  • Commit or merge release files only when the release snapshot is coherent.
  • Verify production deploy before creating the public tag and release.

Hotfix release

  • Branch from main.
  • Fix the issue and add a patch changeset.
  • Merge the fix, consume its patch changeset, and ship a patch release immediately.
  • Use a GitHub security advisory if the fix is vulnerability-related.
  • Backfill any public explanation after disclosure is safe.
