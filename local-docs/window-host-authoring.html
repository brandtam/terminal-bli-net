Adding an app to Terminal

The Window Host authoring guide. After the Slice 6 collapse the OS holds zero app-specific knowledge: an app is a manifest entry plus a zero-prop component, and nothing else. No OS file is edited to add one.

The one rule

Every window in the OS resolves through a single function, matchWindow(id) (in app-catalog.ts). It reads the flat windows[] array on each app manifest and returns { appId, spec, args }. From that one funnel hang every path: render (resolveWindow → WindowHost), geometry (getWindowDef), menu-bar identity (synthWindowAppId), launch (synthAppWindowId), and restore (isKnownWindowId).

So adding an app means adding a manifest with a windows[] entry. The funnel does the rest. The guardrail test zero-os-edit.test.ts registers a brand-new app at runtime and proves the OS resolves/routes/launches/renders it with no OS edit — if a future change reintroduces an app-specific branch, that test catches it.

The AppContext contract

Every app window receives one Svelte context, typed as AppContext in os-context.ts. The live core is { os, fs, window, storage }. storage is a reserved handle until #29 lands. capabilities? and lifecycle? are typed documentation seams only: capability enforcement waits for a future iframe sandbox, and lifecycle hooks wait for the #30 games loop. 

// src/lib/os/os-context.ts
type AppContext = {
  os: OsApiClass;
  fs: TerminalFS;
  window: WindowHandle;
  storage: AppStorageHandle;
  capabilities?: AppCapabilities; // unenforced until sandboxing exists
  lifecycle?: AppLifecycle;       // designed with #30, not before
}

Worked example — Welcome

Welcome is the reference app. It is one fixed manifest window, and its component drives the real OS through ctx.os instead of simulating the tour. 

// src/lib/terminalos/apps/manifests.ts
defineApp({
  id: 'welcome', name: 'Welcome', fileName: 'Welcome.app',
  category: 'system', description: 'Guided tour and reference app',
  icon: '★', iconKind: 'doc',
  removable: false, desktopAliasByDefault: false, isSystem: true,
  windows: [
    {
      match: { kind: 'exact', id: 'welcome' },
      role: 'app',
      title: () => 'Welcome.app',
      size: () => ({ w: 460, h: 540 }),
      component: () => import('$lib/apps/welcome/WelcomeWindow.svelte')
    }
  ],
  menus: (os) => [ /* … */ ],
  aboutSpec: { title: 'Welcome', /* … */ }
})

And the component takes zero props:

// src/lib/apps/welcome/WelcomeWindow.svelte
import { getAppContext } from '$lib/os/os-context';
const ctx = getAppContext();
function openStore() { ctx.os.launchApp('computer-store'); }
// read ctx.os, ctx.fs, ctx.window.args, ctx.storage — never $props()

The WindowSpec contract

One entry in windows[] (full type in app-manifest.ts):

match — { kind:'exact', id, args? } for a fixed window, or { kind:'prefix', prefix:'foo:', arg:'fileId' } for one minted per document. The minted separator is always : (matches chat:, player:, textedit:) — never a new - prefix. An exact window may carry static args (Finder vs Trash are one component on { folder }).
role — 'app' | 'prefs' | 'about' | 'chrome'. Routing only. 'app' marks the launch window (getAppWindowId finds it); 'prefs' marks the ⌘, dialog. Otherwise cosmetic.
title(ctx) / size(ctx) — pure functions of ctx = { args, fs }. No os: they run before the window (and its reactive context) exists. Reading a module store is fine (VCR reads vcrPrefs.device for its deck/size).
component — () => import('…'), lazy so the chunk loads only when the window opens. Returns { default: Component }.
chromeless? — the window draws its own frame (Stickies). Desktop reads it off the resolved spec; no hardcoding.
opens? — declare { contentTypes?, fileTypes? } ONLY if this window is a document handler (the Player opens video). A chrome/launch window must NOT declare opens — it silently steals content-type routing. Two windows claiming one type throws at load.

Rules of thumb

  • Zero props. Components read ctx.os/ctx.fs/ctx.window from getAppContext(); params come from ctx.window.args.<name> (parsed by the matcher).
  • Module state needs invalidation. If size/component depend on mutable module state (a device, a theme), call invalidateWindow(id) when it changes — resolveWindow is memoized by id. (Import it from os/window-host-cache, the leaf module, if your store is loaded early — avoids a load-order cycle.)
  • About boxes are free. Fill aboutSpec; openAbout('yourapp') mints about:yourapp on the system app automatically. No per-app About window.
  • Don't add a fixed window/idPrefix/about/prefs field — those legacy fields are gone. Everything is windows[].
  • Don't reach into an OS file for your app. If you feel the urge to add a startsWith('yourapp-') anywhere, stop — the zero-OS-edit proof test exists to forbid exactly that.

Documented escape hatches

These are the current exceptions to the otherwise-uniform app surface. They are local infrastructure, not app prop drilling:

  • recorder-state.svelte.ts owns the Camera REC badge. The menu bar reads it through manifest statusExtra; no window props are involved.
  • stickies-manager.svelte.ts creates and updates sticky-note files for the custom Stickies launch handler. Notes still render through sticky:<noteId> and AppContext.
  • SYS7_PATTERNS is a static wallpaper constant used by System Preferences, not per-app runtime state.
